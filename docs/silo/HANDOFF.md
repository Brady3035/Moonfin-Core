## The project

Brady contributes to Moonfin (Flutter Jellyfin/Emby client) and Silo Media Server. This fork (`Brady3035/Moonfin-Core`, branch `Silo-Support`; upstream `Moonfin-Client/Moonfin-Core`) adds Silo as a third server type using Silo's native **`/api/v2`** API. The work will be proposed to the Moonfin maintainers later, so every step is documented for review.

## How we work (Brady's rules)

1. **One step = one commit**, titled `silo(<id>): <title>`, with its doc update in the same commit. Granular: never ship two features together. A fix to a step already pushed is its own commit with the step's id (`silo(6.11): Fix …`), documented in that step's section: a Fail row for Brady's test, then the fix row. **Fixes go on top of Brady's HEAD (Brady, 2026-10-18):** a fix is a new patch against the current HEAD, never a rewrite or amend of an earlier commit. Deliver it as a plain `git diff` file named `silo-<step>-fix-<what>.patch` (not `git format-patch`), like the others.
2. **Claude builds, Brady tests and commits.** Brady runs the manual test plan on his Mac plus the full suite (`flutter test` at the repo root). Claude runs targeted tests and the analyzer in its own copy. **Claude doesn't run the full app suite** (Brady, 2026-10-15): it takes over 15 minutes in Claude's workspace and stalls the session. Run the package tests (`server_silo` etc.), the analyzer and the app test files a step touches, and put the full suite in Brady's test list.
3. **Batches (since phase 5).** Claude builds several steps at once as separate local commits, delivers one patch per step, and gives one big test list. Brady tests, then commits step by step:
   `git apply --index .git/silo-<step>.patch && git commit -m "silo(<step>): <title>"`.
   Within a batch each step's commit marks the previous step ☑ with commit `—`; the **first step of the next batch fills in the real hashes** (phase file and ROADMAP tick).
4. Each step is handed over as ◐ Ready for testing with How it works, Testing and a Results row filled in.
5. If something new comes up (a missing case, a plan change), raise it rather than silently widening the step.
6. No feature flag (D8): Silo is a normal server type on this fork.
7. **New UI strings:** add to `lib/l10n/app_en.arb` and commit the regenerated `lib/l10n/app_localizations*.dart`. The stale `ca`, `fi`, `pt` (and `hu`) files get only the new getters inserted, not a full regeneration.
8. **Platform-specific checks wait until the end:** anything needing a TV, phone or other device goes into the "Deferred platform checks" table in step 17.5 (`phases/17-launch.md`), and the step's Results row says it was deferred.

## Where things stand (2026-10-20 evening, performance pass)

Brady asked for a pass over the fork's code for redundant network calls and slow paths, keeping behaviour. Commit `silo: Remove the main-profile sign-in; performance pass`. What changed:

- **A title's page reads its detail once.** The page, its trailers, its extras, its theme songs and the media info each read `GET /catalog/items/{id}` (four or five identical reads per page). `SiloItemsApi.detailJson` keeps the detail 10 s and shares it; seasons lists and season episode lists are kept the same way. Each caller gets its own copy. Anything that changes the catalog or user data forgets them (`noteCatalogChanged`, which `noteUserDataChanged` calls).
- **Refreshing watched state reads lists, not one detail per episode.** `getItems(ids:, fields: 'UserData')` (the 9.4 refresh on returning to a page, the 13.3 read-back) takes two or more episodes of a season from the season's list and seasons from their series' list. Returning to a season after watching an episode was one detail read per episode on the page; it is now one list read.
- **The events socket renews without throwing the caches away.** Silo ends each connection after five minutes, and the snapshot frames of every new connection cleared every kept list. A renewal on schedule now fetches its ticket while the old connection still delivers and drops the new connection's snapshots; a real reconnect still clears.
- **Session start reads the account once.** `getCurrentUser` and `getHousehold` share the `account/me` + `profiles` read (kept 5 s, forgotten when the login or its access changes).
- **Artwork for unseen items** goes through `getItem` (sharing the detail read) and the cached library list instead of raw reads; the library list cache is a `SiloKeptReads` now.
- **A season queued for download** lists the device's entries once instead of once per episode (kept 10 s, new entries put in, forgotten on removal and on a login change).
- **Storing the household at every start** no longer rewrites the whole auth store once per unchanged profile.

### What phase 9 found

- **Retry safety** (contract `x-silo-retry-safety`): favourites, watchlist and dismissals are `natural_idempotent`; watched, ratings and collection writes are `non_retryable` (a repeat adds history, moves the rating time, or makes a second collection). The Silo client has no automatic retry (only a `401` replay before Silo acted), so each write goes once.
- **Ratings are whole stars 1–5** (not 0–10 as the old placeholder said). Moonfin's 0–10 is halved and rounded half up (3½ → 4), at least 1; thumbs up = 5, down = 1. The detail's `user_rating` reads back as `Rating` = stars × 2; there are no likes, so thumbs follow the rating (≥ 6.5 = liked). Half stars aren't kept. `GET /capabilities/ratings` is about external rating sources, not needed.
- **Mark watched** zeroes the resume point; a season or show marks every episode; unmark also hides history up to now.
- **No batch item read on Silo.** `userDataSync.refreshFromServer` asked for every card a screen holds after any change (300 detail reads for a scrolled grid). 9.4 adds `UserDataRefreshScope`: Silo narrows the refresh to items this client changed in the last 10 minutes plus their show's seasons and episodes. Changes from other devices show on reload until realtime (phase 13).
- **Every write clears the Silo-side caches** (`SiloItemsApi.noteUserDataChanged`): home sections, read-once lists, runtime counts, pager.
- **Editable collections** = personal, `collection_type` `manual`, `creator_profile_id` the acting profile (Silo web's rule; fails closed without a profile). `EditableCollectionsApi` limits the add dialog and the *Remove from collection* entry. Adds use `position: 0`, as Silo's web app; adding a title twice is a no-op on Silo.
- **Dismissals** need the card's exact `progress_updated_at` (compared to the second) for Continue Watching and `series_id` for Next Up; an episode drops its whole show from both rows until it's played again. On Silo the hide no longer marks the item unwatched (that would erase history); a refused hide falls back to the device's list.

## Lessons from phases 5–7 (Silo behaviour worth knowing)

- **Cursors are bound to `limit`.** Silo signs every catalog cursor (next and window) over the whole query including `limit`; any other limit gets `invalid_cursor`. `SiloPager` therefore always asks for `pageSize` (100) and serves Moonfin's ranges from kept pages; multi-page ranges seek in parallel (4). The fake list in `silo_pager_test.dart` enforces the binding. Any new paged endpoint should go through the pager.
- **Rule groups** (`groups` JSON on `/catalog`, also accepted by `/catalog/letters`): fields and ops are in `query_definition.go`. `status` is the metadata match state; the airing state is the card's `show_status` and has no rule.
- **Sort titles:** cards carry no `sort_title`; Silo's default moves a leading The/A/An to the end, and `siloDefaultSortTitle` mirrors it for `SortName`.
- **Letter index:** `POST /catalog/letters` gives each letter's position in the title-sorted list for the same library/type/groups.
- **Artwork:** signed URLs only arrive inside items; `SiloImageRegistry` records them, unseen items get placeholder URLs resolved on demand (D2, 6.3); the image cache keys signed artwork by path (6.2).
- **Ids:** library and person ids are both numeric; synthetic ids for genres, studios, collections (`silo_ids.dart`); season/episode ids parse from the id itself.
- **Libraries:** Silo's `/user/libraries` doesn't apply `ui.library_order`/`ui.disabled_library_ids` for unrestricted profiles, so the client does (6.4).
- **Playback info without a session:** 6.18 builds media sources from the item and estimates direct play; it never calls `/playback` (phase 10 does).
- **Search (7.1):** `q` on `/catalog`, ranked by relevance when no `sort` is sent. Episodes only come in a text search, via `type=video_with_episodes` (check `video_with_episodes_scope` in `/catalog/search/capabilities`, read once per 10 min by `SiloItemsApi.searchCapabilities()`). PostgreSQL search drops stop words ("the" finds no titles). Search episode cards carry `series_id`, `series_title`, `season_number`, `episode_number`. No seasons or collections in search results.
- **People search (7.2):** `/catalog/people?q=&media_scope=` matches word starts but returns matches sorted by name, not exact matches first.
- **Probe fixtures beat hand-written ones:** the hand-written trickplay guess had the wrong URL path; prefer asking Brady for a probe run early in a step.

## Key design points so far

(Phases 0–4. Phase 5–6 points are in "Lessons from phases 5–6" above.)

- **Packages:** `packages/server_silo` (client, APIs, mappers) and `packages/playback_silo` (stub until phase 10). The Silo client translates Silo responses into the Jellyfin `BaseItemDto`/`UserDto` shapes the app already reads.
- **Auth (2.1–2.4):**
  - token pair with a rotating refresh token;
  - single-flight refresh (`SiloSession`) and an interceptor that refreshes early and replays a 401 once;
  - sign-in, refresh and PIN calls are never replayed;
  - requests are identity-stamped so nothing is replayed as someone else;
  - only a refused refresh (401) ends a session.
- **Profiles (D9):** household profiles are an optional final phase (18). Until then Moonfin acts as the account's **main (primary) profile**: `useMainProfile()` sends its `X-Profile-Id`, and the Moonfin user id is the main profile's id.
- **App side (3.1–3.5):**
  - `PrivateUser.siloAccountId`;
  - token pairs stored per (server, account) in `AuthenticationStore.siloAccounts`;
  - `SiloTokenStorage` (`lib/auth/services/silo_token_storage.dart`): `bind` saves every refresh; `restore` puts pair, profile and binding on a client. **Every place that hands a stored login to a client must use `restore`, never `client.accessToken = user.accessToken`**, which would drop a live refresh token;
  - a refused refresh forgets the pair and returns to sign-in.
- **User configuration (2.7):** library order and hidden libraries map to Silo settings `ui.library_order` and `ui.disabled_library_ids`. Changed keys only, written at profile scope. "Hide from Latest" has no Silo setting; the switch is hidden for Silo (D11, 8.3).
