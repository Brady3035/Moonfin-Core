# Silo Media Server: native support plan for Moonfin

Branch: `Add_silo` · Target: feature parity with what Moonfin already does on **Emby**
Silo contract used: **native `/api/v2`** (OpenAPI 3.1 at `GET /api/v2/openapi.json`; source copy in
`Silo-Server/silo-server` → `contracts/api/v2/openapi.json`). Silo's Jellyfin-compat listener (port 8096) is
**not** used by this work.

---

## 0. TL;DR: the shape of the work

1. **New packages** `packages/server_silo` and `packages/playback_silo`, mirroring `server_emby` / `playback_emby`.
2. **`ServerType.silo`** is added, which breaks every exhaustive `switch (serverType)` in the app on purpose,
   so the compiler finds each place that has to handle Silo.
3. **A translation layer is the core of the job.** The whole app reads Jellyfin/Emby `BaseItemDto`-shaped maps
   (`AggregatedItem.rawData['Name']`, `['ImageTags']`, `['UserData']`, `['MediaSources']` …). The Silo client
   converts every Silo response (`content_id`, `poster_url`, `user_data`, `versions` …) into that PascalCase shape
   before returning it. The UI, view models and row builders then work unchanged.
4. **Three Silo concepts have no Jellyfin equivalent** and need real design work:
   - **Images.** Silo returns signed, expiring artwork URLs inside the item. It has no `/Items/{id}/Images/{type}`
     route that can be built from an ID. → An image URL registry in the Silo client.
   - **Pagination.** Silo pages with cursors (`next_cursor`, or `window_cursor` + `seek`). Moonfin asks for
     `startIndex/limit`. → A cursor/window cache in the Silo items API.
   - **Playback.** Silo decides the route on the server (`POST /playback/start` with client codec evidence →
     plan + session). There is no `PlaybackInfo` + `DeviceProfile` negotiation, and progress and stop are
     sequenced and idempotent. → A new resolver, a session service, and a translator from DeviceProfile to Silo capabilities.
5. **Auth is token-pair + household profiles.** It uses a Bearer access token with a refresh token, an
   `X-Profile-Id` header on almost every call, and an optional `X-Profile-Token` for PIN-locked profiles.
   → A refresh interceptor, plus extra credential fields.
6. **Moonfin server plugin features don't exist on Silo** (`/Moonfin/*`: settings sync, Seerr proxy, TMDB,
   MDBList, bookmarks, anime markers, custom rows, themes, messages, ratings…). Gate them off for Silo, as
   is already done for Emby in several places.
7. **Not supported on Silo (permanent product decisions):** Live TV / DVR / IPTV, music
   (artists/albums/instant mix/lyrics), playlists, SyncPlay (Silo has its own "Watch Together", left for later),
   Jellyfin admin dashboard.

### 1.2 Silo facts that drive the design

- Native API **`/api/v2`** is the stable 1.0 contract. `/api/v1` is a frozen alpha that will be retired with
  `410 client_upgrade_required`. **Build against v2 only.**
- Native listener default container port 8080 (compose maps host **8090**). Jellyfin compat listens on **8096**, and
  its `/System/Info/Public` says `ProductName: "Jellyfin Server"`. Pointing Moonfin at 8096 today "works" as
  Jellyfin; the native path must win when the user gives the native address.
- Auth: `bearerAuth` (`Authorization: Bearer <access_token>`). `POST /auth/login` → `{access_token, refresh_token,
  expires_in, user}`. `POST /auth/refresh {refresh_token}`. A `401 token_refresh_required` means refresh and retry once,
  and a `503` means keep the tokens and retry after `Retry-After`.
- Device headers: `X-Silo-Device-Id`, `X-Silo-Device-Name`, `X-Silo-Device-Platform` on sign-in. Playback also accepts
  `X-Device-ID`, `X-Client-Name/Version/Platform/Model/OS-Version`, `X-Silo-Client*`.
- Profiles: `GET /profiles`. Most viewer routes **require** the `X-Profile-Id` header. PIN → `POST
  /profiles/{id}/verify-pin` → `profile_token`, sent as `X-Profile-Token`.
- IDs: `content_id` (string) for items, `file_id` (string) for media files/versions, season IDs may be
  `<series>-S<number>` when the season has no stored metadata.
- Time is **seconds** (float). Jellyfin uses **ticks** (×10,000,000).
- Images: `poster_url`, `backdrop_url`, `logo_url`, `still_url`, `photo_url` (signed or presigned, relative
  `/api/v2/artwork/{key}` or absolute S3). `image_size=small|medium|large|original` per request. Revisioned URLs
  are stable for a UTC day. Other URLs rotate every ≤15 min, so **cache by path, not full URL**.
- Discovery: mDNS/DNS-SD `_silo._tcp`, TXT `id` = server id. Verify with `GET /api/v2/system/identity`.
- Realtime: `POST /events/ws-ticket` → connect `GET /events/ws` with subprotocols `silo.events.v2`,
  `silo.ticket.<ticket>`. Connections last ≤5 min, so reconnect with a fresh ticket.
- Product non-goals (from Silo's `CLAUDE.md`): **no Live TV/IPTV/EPG/DVR/.strm, ever**. 1.0 library scope is Movies +
  Series. Audiobooks/ebooks/manga are "beta". No music, no playlists.

      Moonfin's probe already rejects non-JSON, so probing `/api/v2/system/info` first is enough. Add a test for the HTML case.
- [x] **Two different server ids.** `/api/v1/health` reports `b2d9e6c9-…` and `/api/v2/system/identity` reports `7b72fbd5-…`.
      Store the **v2 identity**, never the v1 one.
- [x] **ID shapes.** Library `"1"` (small numeric string), item `movie-imdb-tt0295701` (deterministic, readable),
      file `"4598"` (numeric string), person `"146552272560604468"` (snowflake string), home section ids are snowflake strings.
      All are strings; keep them opaque.
- [x] **Artwork URLs** are `/api/v2/artwork/<provider>/<kind>/<id>/<slot>/w<width>.<sha256>.webp?exp=<UTC midnight>&sig=…`.
      This confirms §5.6: the path carries the revision and the query only authorizes, so cache by path. **New:** cast and crew
      `photo_url` is often an **absolute, unsigned `https://image.tmdb.org/...` URL**, so the registry must pass external
      absolute URLs through unchanged.
- [x] **Home layout on this server has no `next_up` section** (Movies-only library). `getNextUp` must tolerate the section
      being absent, and return empty rather than throw.
- [x] **Playback start (web player, Chromium) returned:** `delivery: server_remux_progressive` (MKV/HEVC/DTS → MP4/HEVC/AAC
      stereo), `stream.headers: {}`, `header_refresh: none`, URL signed with `st=`. The web player **adds `token=<access token>`**
      to the stream URL and every subtitle sidecar URL. So the signed `st` alone is not what the web client relies on: Moonfin
      appends `token=` to `/api/v2/stream/...` URLs (§7.2 step 7). Test whether `st` alone is accepted (it matters for casting, §8.6).
- [x] **`timeline.can_seek_anywhere: false` on a progressive remux.** Seeking outside what has been produced needs a
      **replan** (`seek_reanchor_v1`). Replan is therefore **required in the first playable version** for remux deliveries,
      not a later improvement (§7.2 "Replan").
- [x] **Track identity, three numbering schemes for the same file:**
  - Emby `MediaStreams[].Index` follows **container order**: audio=0, video=1, subtitles=2,3.
  - Silo `/watch` `subtitle_tracks[].index` = **2,3** (the same container index). But `audio_tracks` / `video_tracks` carry
    **no container index**, and `effective_audio_track_index: 0` is an audio-only ordinal.
  - The Silo playback plan uses ids `file:4598:audio:0` and `file:4598:subtitle:0`, where the subtitle number is the
    **subtitle-only ordinal** (`inventory[].combined_index` 0,1), not 2,3.

  → The §5.3 mapper must: keep Silo's subtitle `index` as the Jellyfin `Index`; give video and audio the lowest indices not
  used by subtitles (video first, then audio); and store a map `jellyfinIndex → {kind, ordinal, trackId}` so the resolver
  sends `audio_track_index` / subtitle `track_id` and reverse-maps `selected_tracks`. A golden test against
  `emby/item_movie_xxx.json` is not possible for the audio/video order (Emby has audio=0), so assert by type and ordinal instead.
- [x] **`trickplay_available`** is a per-version boolean in `/watch` (missing from my first reading of the schema). Only call
      `/watch/{id}/trickplay` when it is true.
- [x] **No `DELETE /playback/{session}` was observed** when the web player was left by navigation (progress only). The server
      expires abandoned sessions, but Moonfin should still stop explicitly (§7.2).
- [x] **`chapters`** on a version carry `start_seconds`/`end_seconds`/`title`/`source`; Emby has `StartPositionTicks`/`Name`/`ImageTag`.
      No chapter thumbnails on this file (no `thumbnail_url`).
- [x] **TV samples (Young Justice, 4 seasons, on both servers):**

## 4. Phase 2: authentication, session and profiles

### 4.1 Login flow (UI → repo → client)

Moonfin today: server select → (public users `/Users/Public`) → login screen → `authApi.authenticateByName` →
`{AccessToken, User, ServerId}` → `client.accessToken/userId` → credential store.

Silo flow to implement:

1. Server added, probe says `silo`.
2. **No public user list.** `lib/auth/repositories/server_user_repository.dart` must return `[]` for Silo (do not call
   `/Users/Public`), and the login screen shows username/password directly. Optionally show branding
   `login_subtitle` / `login_bg_url`.
3. `SiloAuthApi.authenticateByName` → `POST /api/v2/auth/login {username,password}` with device headers.
   Translate to the Jellyfin `AuthenticationResult` shape the repo expects:
   `{AccessToken: access_token, ServerId: <identity.server_id>, User: <translated account>, SessionInfo: {}}`
   and **also** return `_silo: {refresh_token, expires_in, issued_at}` for the repo to persist.
4. **Profile selection.** `GET /api/v2/profiles` (no profile header needed). If exactly one profile without a PIN,
   auto-select it. Otherwise push a new **"Who's watching?"** screen (`lib/ui/screens/auth/silo_profile_select_screen.dart`)
   that reuses existing user-avatar tiles. A PIN profile → PIN pad → `verify-pin` → store `profile_token` +
   `expires_at`. Handle `429` lockout using `Retry-After` text (do not auto-retry, the endpoint is non-retryable).
5. `password_change_required: true` → show a blocking change-password dialog (`POST /account/password`) or a message
   telling the user to do it on the web (minimum).

### 4.2 Identity mapping decision (needs your sign-off)

| Option | Moonfin `userId` | Pros | Cons |
|---|---|---|---|
| **A (recommended)** | Silo **profile id**, with the account id stored alongside | The existing multi-user switcher, avatars, per-user prefs, offline DB partitioning and "last user" all work per household member, like Netflix | Several Moonfin "users" share one token pair, so refresh must update all of them |
| B | Silo account id; profile is a sub-setting | Simpler storage | Per-member prefs, history and avatars collapse into one user. Switching profiles needs new UI |

**Decided (2026-10-08): option A.** Each Silo household profile appears as its own Moonfin user.

#### 4.2.1 Design note: households inside Moonfin's multi-server model

Moonfin's user model assumes **one server user = one login = one token**. Silo breaks that: **one login (account) =
one token pair = several profiles**. Mixing the two needs explicit rules, because each of these places assumes the old model:

| Where | What Moonfin does today | What goes wrong with profiles as users | Rule for Silo |
|---|---|---|---|
| `SessionRepository.destroyCurrentSession` | Calls `authApi.logout()`, deletes the server's token (`_credentialStore.deleteToken(serverId)`), removes that one user | `POST /auth/logout` revokes the **account** session, so every sibling profile on that device is signed out too, while the store still lists them | Split the two actions. **Switch profile** only changes `X-Profile-Id`: no logout, no token deletion, same client. **Sign out of a profile** removes that user from the list, and calls `logout` and deletes the token only when it was the account's last remaining profile. Add a separate **Sign out of account** that removes all of its profiles at once. |
| Credential store | Token slot keyed by **server id** | Two Silo accounts on the same server (for example one per family) would overwrite each other's token | Key Silo tokens by `(serverId, siloAccountId)`, and store `siloAccountId` on each Silo `PrivateUser`. Check how Jellyfin multi-user per server already copes (each `PrivateUser` carries its own `accessToken`) and reuse that if it suffices. |
| Token refresh | Not needed (Jellyfin/Emby tokens don't expire) | A refresh rotates the token pair; sibling profiles that cached the old pair would 401 | Refresh writes the new pair once per account, and every profile of that account reads it from there. Never copy tokens into individual profile users. |
| `MediaServerClientFactory` | One client per server | Fine: one client, `profileId` set per active user | Profile switch = set `profileId`/`profileToken` on the existing client, then reload user-scoped state (home rows, views, user data). |
| `MultiServerRepository` (`ServerUserSession`: one user per server for cross-server home/search) | Picks one user per server | With several stored profiles on one Silo server, which profile's watch state and parental limits feed the merged rows? | Use the **active** profile for the active server, and the **last-used profile** for other Silo servers. Never merge profiles of the same household into one row (they are the same library with different watch state and restrictions). |
| User picker / auto-login (`savedAutoLoginUserId`, `lastUserId`) | Per user | A PIN-locked profile must not auto-login without its proof | Auto-login only into profiles without a PIN, or with an unexpired `profile_token`. Otherwise show the PIN pad. |
| Offline DB / downloads (rows keyed by `serverId` + user) | Per user | Downloads made under a child profile should not surface under the parent's account context unexpectedly, and the reverse | Keep downloads keyed per profile (the Moonfin user id), as they are today. Revisit only if users ask for household-shared downloads. |
| Server list UI | Server → users | A household shows as several users of one server, which is correct, but a second account on the same server looks identical | Show the account username as a subtitle on Silo profile tiles when more than one account is stored for that server. |

Open question for implementation: the user switcher today mixes "users of this server" and "other servers". With
profiles it should group as **server → account → profiles**. Grouping only by server is acceptable for v1 if account
subtitles are shown.

The rest of this plan assumes **A**.

### 5.6 Image URL registry (`silo_image_registry.dart`)

**Problem:** 90+ call sites build images through `imageApi.getPrimaryImageUrl(itemId, tag:, maxWidth:)` and expect
a URL computable from `(itemId, type, tag)`. Silo only gives signed URLs embedded in payloads.

Design:

- [ ] While mapping, for each artwork slot: `tag = shortHash(urlPath)` (path only, so daily-rotating query strings
      keep the same tag), then `registry.put(itemId, ImageType, index, sizeVariant, absoluteUrl, thumbhash)`.
- [ ] `SiloImageApi.getPrimaryImageUrl(itemId, tag:, maxWidth:)` → registry lookup; choose the `image_size` bucket from
      `maxWidth` using the ladder from `GET /images/capabilities` (poster: 300/500/780/1920 …).
- [ ] **Miss handling:** the registry has nothing for that item (cold start, offline DB, deep link). Return a
      **resolver URL** such as `silo-image://<itemId>/<type>?w=…`, handled by a custom `ImageProvider` / cache-manager hook in
      `packages/cached_network_image_fork` that calls `GET /catalog/items/{id}?image_size=…`, fills the registry and
      then loads the real URL. (Alternative: the miss returns `''` and the UI shows a placeholder. Simpler, but artwork
      disappears after restarts.)
- [ ] Relative URLs (`/api/v2/artwork/...`) → prefix `baseUrl`. Absolute S3 URLs → leave as is. **Never** append a token.
- [ ] Cache key = URL **path** (strip the query) for revisioned artwork, so the daily URL change doesn't refetch every image. Check
      `cached_network_image_fork` supports a `cacheKey` override, and pass it.
- [ ] Expiry: non-revisioned URLs rotate every ≤15 min. On image `404`/`403`, invalidate the registry entry and re-resolve once.
- [ ] Persist the registry (LRU, size-capped) so a cold start shows home artwork before the first fetch completes,
      or accept one round trip.
- [ ] `getUserImageUrl(userId)` → profile `avatar_url` (registry keyed by profile id). `user_menu_dialog.dart:106`
      builds `/Users/{id}/Images/Primary` by hand, so route it through `imageApi`.
- [ ] `getBannerImageUrl`/`getThumbImageUrl`: Silo has no separate thumb/banner. Thumb → backdrop (or episode still),
      Banner → backdrop. Document this so landscape cards look right.

## 7. Phase 5: playback (`packages/playback_silo`)

### 7.1 How Silo playback differs

| Jellyfin/Emby (Moonfin today) | Silo v2 |
|---|---|
| `POST /Items/{id}/PlaybackInfo` with a `DeviceProfile` → server lists sources with DirectPlay/DirectStream/Transcode URLs; the client picks | `POST /playback/start` with **codec evidence** (`client_capabilities` + `client_playback_context`) → server returns **one plan**: `delivery`, `stream.url`, `stream.headers`, `subtitle`, `timeline`, `session_id` |
| Progress: `POST /Sessions/Playing/Progress` (fire-and-forget) | `POST /playback/{session_id}/progress {installation_id, sequence, position, is_paused}` (monotonic sequence) |
| Stop: `POST /Sessions/Playing/Stopped` | `DELETE /playback/{session_id} {installation_id, stop_id(uuid), sequence?, position?, is_paused?}` |
| Change audio/subtitle/quality → new PlaybackInfo + new URL | `POST /playback/{session_id}/replan {replan_request_id, …}` |
| Ticks | Seconds |

- Music libraries, artists, albums, instant mix, lyrics (not in Silo)
- Playlists (not in Silo; personal collections are the closest)
- SyncPlay (Silo's Watch Together is a different protocol, so it gets its own future project)
- Remote control of other sessions
- Admin dashboard for Silo (Silo's admin API is huge and separate; use Silo's web admin)
- Moonfin server-plugin features (Seerr proxy, settings sync, TMDB/MDBList proxies, bookmarks, anime markers, custom rows, themes, messages)
- Silo `/api/v1` (frozen alpha)

## 15. Open questions to settle early

1. **Identity mapping** A (profile = Moonfin user) vs B (§4.2).
2. **Image miss strategy**: resolver-URL `ImageProvider` vs placeholder (§5.6).
3. **Track changes**: implement `replan` (best) or stop + start (simplest) first (§7.2).
4. **Display preferences**: server-side via `/settings/values` or local only (§6.8)?
5. **Thumbhash** placeholders: add a decoder or drop placeholders for Silo?
6. Does your Silo deployment run distributed (separate proxy/transcode origins)? This affects stream auth (§0.6, §7.2).
7. Upstream PR scope: do the `server_core` interface additions (profile fields, `authHeaders()`, `timelineOffset`, optional `replan`)
   suit the Moonfin maintainers? Open an issue or discussion on `Moonfin-Client/Moonfin-Core` before the large PR.
8. Silo's own contribution rules: their `CLAUDE.md` requires an AI-use disclosure on PRs **to Silo**. That doesn't apply to Moonfin,
   but if we find Silo API gaps (for example a bulk `ids` lookup), file issues upstream rather than working around them silently.
